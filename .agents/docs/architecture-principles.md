# Архитектурные принципы Tablo

## 1. Tablo — SaaS-платформа

Kafema Kurort / Кафема Санаторная — первый tenant, а не модель всей системы.
Любая функция должна допускать сотни заведений, точки внутри сети и несколько
пользователей без копирования приложения.

## 2. Platform и tenant разделены

- Tablo хранит глобальные возможности платформы.
- Tenant хранит бренд, интеграционные реквизиты и настройки заведения.
- Пользовательские данные имеют tenant scope.
- Клиентская витрина показывает бренд заведения; Manager и Bar используют
  бренд Tablo согласно своей роли.

## 3. iiko — операционный источник истины

iiko владеет:

- товарами и категориями;
- ценами;
- размерами и модификаторами;
- стоп-листами и наличием.

Tablo не превращается во вторую учетную систему.

## 4. Overrides — отдельный слой представления

Tablo может хранить фото, красивые названия, описания, видимость, сортировку и
бейджи. Overrides накладываются на iiko snapshot и не стираются
синхронизацией.

```text
iiko source data
       +
Tablo tenant overrides
       ↓
Storefront view model
```

## 5. Один источник истины

Не создавать отдельные модели одной сущности для Client, Bar и Manager.
Интерфейсы могут иметь разные view models, но читают общую бизнес-модель и
подтвержденные данные.

## 6. Конфигурация важнее хардкода

Organization, terminal group, External Menu, бренд и настройки точки должны
приходить из tenant config или Manager. Пилотный хардкод допустим только как
явный временный долг с путем миграции.

## 7. Надежность важнее удобного happy path

- Оплаченный заказ нельзя потерять при недоступности iiko.
- Внешние операции должны быть наблюдаемыми и повторяемыми безопасно.
- Ошибка не должна превращать неизвестное состояние в ложный успех.
- Persistence и конкурентная работа учитываются до production.

## 8. Интерфейсы разделены по ролям

- Client: быстрый мобильный заказ.
- Bar: скорость приготовления и минимум действий.
- Manager: контроль витрины и интеграций.

Функция размещается там, где она помогает конкретной роли.

## 9. Эволюция без параллельной архитектуры

Расширять существующие services, stores и contracts. Новый слой добавлять
только при четкой ответственности. Временный fallback должен быть явным,
ограниченным средой и не становиться вторым production-путем.

## 10. Решения фиксируются

Значимое изменение источника истины, хранения, tenant-модели или внешнего
контракта оформлять через `../templates/architecture-decision.md`.
