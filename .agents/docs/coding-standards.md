# Стандарты разработки Tablo

## Изменения

- Сначала читать код и все места использования, затем редактировать.
- Делать минимальное изменение в правильном слое.
- Следовать существующим именам, типам и паттернам.
- Не смешивать feature, bugfix и refactor в одном diff.
- Не удалять и не откатывать неизвестные изменения.

## Источники истины

- Каждая бизнес-сущность имеет один подтвержденный источник истины.
- iiko отвечает за меню, цены, категории, модификаторы и availability.
- Tablo Overrides отвечают только за витринное представление.
- Derived state вычислять из исходных данных, а не синхронизировать копии.
- Mock использовать только в явно обозначенной test/development среде.

## Компоненты и модули

- Переиспользовать существующий компонент до создания нового.
- Не создавать параллельный service, store или parser.
- Уважать границы Client, Bar и Manager.
- Абстракцию добавлять только при реальном снижении сложности или дублирования.
- Мертвый код удалять только после проверки всех импортов и call sites.

## API и данные

- Секреты и privileged запросы держать server-side.
- Не выводить credentials, bearer tokens и персональные данные.
- Валидировать внешние ответы и неизвестные поля.
- Использовать стабильные ID, не отображаемые названия.
- Для сетевых операций задавать timeout и безопасную ошибку.
- Retry ограничивать и применять только к безопасным операциям.
- Write-операции во внешних системах выполнять только по явному разрешению.

## UI

- Сохранять утвержденный дизайн и tenant-бренд.
- Проектировать mobile first для клиентской витрины.
- Проверять loading, empty, error, success и disabled.
- Не подтверждать оплату, сохранение или синхронизацию до серверного результата.
- Текст должен помогать выполнить задачу, а не объяснять интерфейс.

## Производительность

- Не дублировать fetch и polling.
- Останавливать фоновые процессы, когда они не нужны.
- Использовать кэш только с понятной политикой свежести.
- Не добавлять зависимость без необходимости.
- Не оптимизировать без измеримого или обоснованного риска.

## Проверка

- Не заявлять о работоспособности только по чтению кода.
- Запускать проверки из `package.json`.
- Проверять измененный сценарий фактически.
- Отделять warnings от errors и честно фиксировать непроверенное.
