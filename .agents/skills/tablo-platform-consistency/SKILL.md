# Цель

Сохранить Tablo как масштабируемую SaaS-платформу, не смешивая глобальную
логику платформы с настройками и данными отдельного заведения.

# Триггер

Применить перед изменением архитектуры или поведения, если решение хранит,
читает, синхронизирует или отображает данные конкретного tenant.

# Применять

- При добавлении ресторанных настроек, интеграций и серверного хранения.
- При изменении Admin, общих API, Redis-ключей или источников истины.
- При работе с брендом, доменом, организацией, terminal group или tenant ID.
- При подготовке функциональности к нескольким заведениям и пользователям.

# Не применять

- Для локальной визуальной правки без данных и tenant-зависимого поведения.
- Для аудита производительности, безопасности или UX вместо профильного skill.
- Как основание для большого рефакторинга вне границ задачи.

# Обязательный алгоритм

1. Прочитать `PROJECT.md`, `VISION.md` и затронутые data-flow модули.
2. Определить, какие данные являются глобальными для Tablo, tenant-specific и
   пользовательскими.
3. Найти фактический источник истины, storage, API и все call sites.
4. Проверить код, ключи, тексты и конфигурацию на хардкод пилотного кафе,
   организации, terminal group, домена и бренда.
5. Проверить, не создается ли второй источник истины рядом с iiko, Redis,
   серверным store или существующей конфигурацией.
6. Проверить возможность изоляции нескольких tenant и одновременной работы
   нескольких пользователей.
7. Определить, что должно конфигурироваться, и использовать существующий
   механизм Admin или server-side tenant config.
8. Оценить поведение при добавлении второго заведения без копирования модулей.
9. При проблеме описать ее и предложить минимальное совместимое решение.
10. Не переписывать архитектуру без отдельного согласования.

# Чек-лист

- [ ] Нет хардкода конкретного кафе, если он не является временной явной
  конфигурацией пилота.
- [ ] Бренд платформы отделен от бренда tenant.
- [ ] Tenant-specific данные изолированы и имеют стабильный идентификатор.
- [ ] Новое заведение подключается конфигурацией, а не копированием кода.
- [ ] Существует один подтвержденный источник истины.
- [ ] Общие сервисы не содержат скрытой tenant-specific логики.
- [ ] Настройки вынесены в подходящую конфигурацию или Admin.
- [ ] Учтены persistence, конкурентные изменения и несколько пользователей.
- [ ] Секреты и server-side данные не попадают в клиент.
- [ ] Предложенное исправление минимально и не требует несогласованного
  рефакторинга.

# Итоговый отчет

Указать затронутые platform и tenant границы, найденные хардкоды, источник
истины, способ конфигурации, готовность ко второму заведению и
многопользовательской работе. Для каждой проблемы дать минимальное решение и
явно отметить, было ли оно реализовано или только предложено.
