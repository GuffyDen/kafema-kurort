# Цель

Сделать минимальное изменение в правильном слое, сохранив текущую архитектуру, данные и API-контракты.

# Применять

- Для точечного багфикса или ограниченной доработки.
- При работе с состоянием, storage, API route или общим компонентом.
- Когда в проекте могут существовать legacy, mock и production реализации.

# Не применять

- Для разрешенного большого архитектурного изменения.
- Для аудита без редактирования.
- Как оправдание удаления кода без проверки использования.

# Порядок действий

1. Найти реальную точку входа production-сценария.
2. Проследить связанные компоненты, routes, типы, stores, persistence и call sites.
3. Сформулировать минимальный план и границы изменений.
4. Проверить, нет ли готовой функции или абстракции.
5. Внести минимальное изменение в существующий путь.
6. Удалять старое только после `rg` по всем использованиям.
7. Проверить API-контракт, persistence и client/server boundary.
8. Применить `tablo-regression-check`.

# Чек-лист

- [ ] Не создана параллельная реализация рядом со старой.
- [ ] Mock-массив не используется вместо production-данных.
- [ ] Изменен именно production-компонент или route.
- [ ] Нет двух источников истины.
- [ ] Redis-данные, localStorage и миграции не потеряны.
- [ ] Storefront overrides не стираются синхронизацией.
- [ ] Server env не импортирован в client component.
- [ ] Соседние страницы и визуальный стиль не изменились.
- [ ] Новая зависимость действительно необходима либо не добавлена.

# Правила Tablo

- iiko хранит учетные данные меню; Tablo хранит витринный overlay.
- Заказы, оплата и availability требуют подтвержденного серверного результата.
- Учитывать разделение tenant-бренда и Tablo.
- Не откатывать пользовательские изменения в грязном worktree.

# Итоговый отчет

Указать найденную точку входа, причину дефекта, минимальное решение, измененные файлы, сохраненные контракты и данные, результаты проверок и ограничения.
