# Цель

Сделать каждое действие предсказуемым, защищенным от повторной отправки и честно отражающим серверный результат.

# Применять

- При добавлении или изменении интерактивного элемента.
- При работе с асинхронным запросом, сохранением, удалением или синхронизацией.
- При исправлении двойных кликов, потерянного состояния или ложного успеха.

# Не применять

- Для статического текста без действия.
- Для чистого серверного рефакторинга, не меняющего контракт и состояние UI.
- Как замену полному UX-аудиту.

# Порядок действий

1. Найти обработчик, источник состояния, API route и постоянное хранилище.
2. Составить таблицу переходов: исходное состояние, событие, запрос, успех, ошибка, повтор.
3. Проверить `default`, `hover`, `pressed`, `focus`, `loading`, `disabled`, `success`, `error`.
4. Определить поведение отмены, повторной попытки, двойного нажатия и обновления страницы.
5. Добавить минимальную блокировку или дедупликацию там, где операция не должна повторяться.
6. Проверить сценарий фактическим кликом и сетевым результатом.

# Чек-лист

- [ ] Loading видим и не меняет геометрию интерфейса.
- [ ] Повторное нажатие не создает дубликаты.
- [ ] Disabled является настоящим HTML-состоянием, а не только цветом.
- [ ] Success показывается только после подтверждения.
- [ ] Error сохраняет введенные данные и предлагает понятный повтор.
- [ ] Focus доступен клавиатуре; touch-цель не стала меньше.
- [ ] После refresh сохраняются только состояния, которые должны сохраняться.
- [ ] Отмена не оставляет UI в loading.

# Особые сценарии Tablo

- Перед добавлением и checkout проверять актуальную доступность.
- Товар, ставший недоступным, нельзя добавить или оформить; остальные позиции корзины сохраняются.
- Не использовать optimistic success для оплаты, создания заказа и доступности.
- Синхронизация и overrides должны показывать реальный результат сервера.

# Итоговый отчет

Перечислить проверенные переходы состояний, защиту от повторов, поведение ошибок и refresh, фактические тесты и непротестированные ветки.
