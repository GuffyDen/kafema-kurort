# Цель

Найти реальные потенциальные узкие места и устранить их минимально, не выполняя
преждевременную оптимизацию.

# Триггер

Применить перед финальной проверкой задачи, если изменение затрагивает сетевые
запросы, рендеринг, кэш, синхронизацию, изображения или критический
пользовательский путь.

# Применять

- После добавления fetch, polling, effects, derived state или тяжелого UI.
- При изменении API routes, Redis, cache policy и серверной синхронизации.
- При работе с изображениями, списками товаров и клиентским bundle.
- Когда есть жалоба на медленную загрузку, скачки интерфейса или нагрузку.

# Не применять

- Для чистой документации и текстовых правок.
- Когда нет измеримого или обоснованного риска производительности.
- Для изменения архитектуры только ради теоретического ускорения.

# Обязательный алгоритм

1. Определить затронутый критический путь: первый экран, выбор товара,
   checkout, Admin или Barista.
2. Проследить все fetch, polling, retries, cache и Redis-операции этого пути.
3. Найти повторные запросы, параллельные дубликаты и polling в неактивном
   состоянии.
4. Проверить `useEffect`, зависимости, derived state, повторные вычисления и
   ререндеры списков.
5. Проверить размер и частоту передаваемых JSON, отсутствие лишних raw payload
   в клиенте и корректность `cache` policy.
6. Проверить Redis round trips, ключи, TTL, блокировки и дедупликацию запросов.
7. Проверить изображения: размеры, формат, lazy loading, fallback и влияние на
   LCP/CLS.
8. Проверить необходимость lazy loading и влияние новой зависимости на bundle.
9. При возможности измерить Network, React/browser behavior, build output и
   Core Web Vitals; отделить факт от предположения.
10. Исправлять только подтвержденную или высоковероятную проблему минимальным
    изменением, затем применить `tablo-regression-check`.

# Чек-лист

- [ ] Нет лишних или повторных fetch.
- [ ] Нет нескольких polling-циклов для одного источника.
- [ ] Polling останавливается, когда данные не нужны.
- [ ] API и Redis-вызовы дедуплицированы там, где это дает реальную пользу.
- [ ] Нет лишних `useEffect` и дублирования derived state.
- [ ] Тяжелые вычисления и большие списки не пересчитываются без причины.
- [ ] Ререндеры не затрагивают несвязанные крупные части интерфейса.
- [ ] Lazy loading используется только там, где улучшает путь пользователя.
- [ ] Изображения не создают лишний трафик, LCP или CLS.
- [ ] Клиентский bundle не получил ненужную зависимость или server-only код.
- [ ] Cache policy соответствует свежести данных.
- [ ] Проверены потенциальные узкие места Core Web Vitals.
- [ ] Нет преждевременной оптимизации без фактической причины.

# Итоговый отчет

Дать таблицу `Проверка | Наблюдение | Риск | Решение`. Отдельно указать
измеренные данные, оптимизированные места, сознательно оставленные участки и
причину, по которой дополнительная оптимизация сейчас не требуется.
