# Цель

Доказать работоспособность изменения проверками, соответствующими его риску, и честно отделить автоматическую проверку от ручной.

# Применять

- После изменения кода, конфигурации или API-контракта.
- Перед commit, push или deploy.
- При запросе QA, smoke или regression-проверки.

# Не применять

- Для задачи, где пользователь прямо запретил запуск кода.
- Для документационного изменения, если проверки приложения не дают полезного сигнала.

# Порядок действий

1. Прочитать `package.json` и определить реальные scripts и package manager.
2. Проверить `git diff --check` и область измененных файлов.
3. Для текущего проекта выполнить `npm run lint`, `npx tsc --noEmit`, `npm run build`.
4. Проверить измененные API routes прямыми запросами без секретов в выводе.
5. Пройти затронутый сценарий в браузере на реальном dev server.
6. Проверить мобильную ширину, если затронут клиентский UI.
7. Зафиксировать warnings отдельно от errors; не ослаблять правила ради зеленого результата.

# Чек-лист

- [ ] `/`: загрузка, пусто, ошибка, карточка без фото, длинное имя, «Нет в наличии».
- [ ] Product configurator: модификаторы, цена, disabled и повторный клик.
- [ ] Cart/checkout: количество, удаление, свежая availability, ошибка и success.
- [ ] `/admin`: загрузка, форма, сохранение, sync, refresh.
- [ ] `/bar`: пустая очередь и затронутые стадии, если экран менялся.
- [ ] API: status, headers, безопасный body и отсутствие cache там, где это важно.
- [ ] Нет новых console/runtime/ReferenceError.

# Правила Tablo

- Не считать code inspection ручным тестом.
- Если Browser недоступен, описать программную проверку и конкретный ручной пробел.
- Для iiko использовать read-only диагностику, если write не разрешен.
- Не включать `.env.local` и временные дампы в Git.

# Итоговый отчет

Дать таблицу `Проверка | Результат | Примечание`, затем перечислить проверенные сценарии, оставшиеся риски и блокирует ли что-либо deploy.
